# EDUCORE AI — PHASE 1: INTEGRATED FOUNDATION

You are building an integrated hackathon platform named **EDUCORE AI — Intelligent Student Success & Academic Management System**.

This is an independent backup implementation covering all three official CodeSpark 2026 Education problem statements:

- PS1: AI-Powered Multilingual Adaptive Learning & Automated Remediation Platform.
- PS2: Automated Formative Assessment and Intelligent Subjective Grading Assistant.
- PS3: AI-Driven Early Dropout Prediction and Student Retention Copilot.

## OBJECTIVE

Build the complete technical foundation for one integrated application containing all three modules.

Do not attempt to implement every advanced AI feature in this phase. Establish a reliable architecture that allows PS1, PS2 and PS3 to be implemented and connected in later phases.

## TECH STACK

Frontend:
- Next.js
- React
- TypeScript
- Tailwind CSS
- shadcn/ui
- Lucide React
- Recharts

Backend:
- Python
- FastAPI
- Pydantic

Database:
- Supabase PostgreSQL

Use environment variables for credentials and provide `.env.example`.

## PHASE 1 REQUIREMENTS

### 1. Main application and dashboard

Create a polished, responsive application with:
- EDUCORE AI branding.
- Sidebar navigation.
- Main overview dashboard.
- Student, teacher, faculty and counselor demo roles.
- Responsive desktop and mobile layouts.
- Consistent design system.
- Loading, empty, success and error states.

The dashboard should display:
- Total students.
- Active students.
- Average learning mastery.
- Pending evaluations.
- Students requiring attention.
- Recent activity.
- Module overview cards.

Use clearly labelled demo data wherever real data is not yet available.

### 2. PS1 module — Adaptive Learning

Create the initial module interface with:
- Student learning dashboard.
- Subject and topic selection.
- Topic mastery meter.
- Knowledge graph visualization placeholder with real sample concept relationships.
- Quiz interface structure.
- Learning progress section.
- Teacher classroom overview.
- Weak-topic and remedial-content section.

Do not fake a completed adaptive learning engine. Clearly separate implemented features from planned functionality.

### 3. PS2 module — Answer Evaluation

Create the initial module interface with:
- Faculty assessment dashboard.
- Create assessment interface.
- Question and reference-answer management.
- Rubric creation interface.
- Student submission upload interface.
- Evaluation results table.
- Evaluation review page structure.
- Faculty moderation and score-override interface structure.

Prepare the UI for PDF/TXT submissions and batch uploads.

### 4. PS3 module — Dropout Prediction

Create the initial module interface with:
- Institution risk overview.
- Student risk table.
- CSV upload interface.
- Student profile page.
- Risk progression chart structure.
- Explainability panel structure.
- Counselor intervention task list.

Use explicitly labelled synthetic demo data. Do not claim actual ML predictions yet.

### 5. Shared student identity

Create a common student model used by all three modules.

Every student must have a stable `student_id`.

PS1, PS2 and PS3 must reference this same identifier.

Prepare database entities for:
- Students
- Users and roles
- Courses and subjects
- Student learning progress
- Assessments and submissions
- Evaluation results
- Student activity snapshots
- Risk predictions
- Counselor interventions

Create appropriate foreign keys, timestamps and basic indexes.

### 6. Backend foundation

Create a FastAPI backend with:
- Health-check endpoint.
- Shared student endpoints.
- Role/user endpoints or a clearly documented demo authentication approach.
- PS1 router.
- PS2 router.
- PS3 router.

Use consistent API responses:

{
  "success": true,
  "module": "ps1",
  "student_id": "STU001",
  "data": {},
  "message": "Operation completed"
}

For errors, use `success: false`, `data: null` and a readable message.

Provide Swagger documentation.

### 7. Integration architecture

All three modules must:
- Use the same database.
- Use the same student identifier.
- Follow consistent API response conventions.
- Use shared components and styling.
- Avoid creating separate independent applications.
- Be designed for future integration with one dashboard.

### 8. Quality requirements

- No non-functional buttons.
- No broken navigation.
- No hardcoded secrets.
- No fake claims about AI capabilities.
- No unnecessary dependencies.
- No unnecessary complexity.
- Make the application easy to run locally.
